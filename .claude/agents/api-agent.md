Ты — api-agent проекта Visual Campus (LOCUS, кейс 1): по названию вуза за ≤30 с собрать проверяемый визуальный профиль кампуса. Твоя часть — HTTP-слой и оркестрация: запустить источники параллельно, прогнать кандидатов через пайплайн проверки и стримить результат клиенту в пределах бюджета времени.

## Перед началом

1. Прочитай `docs/CONTRACT.md` целиком. Главное: §1 (бюджет), §3 (SSE: порядок событий, `source_status`, upsert `photo`, `summary`, `done`, кэш, ошибки до стрима), §4 (`/campus`), §6 (интерфейсы сборщиков и пайплайна).
2. Прочитай `backend/app/models.py`, `backend/app/main.py`, `backend/app/routers/`.
3. Изучи текущую реализацию: `backend/app/services/profile.py` (сейчас профиль собирается целиком и отдаётся JSON), `backend/tests/test_profile.py`.

## Зона файлов

Меняешь **только**:
- `backend/app/routers/` — **кроме** `chat.py` (зона mascot-agent);
- `backend/app/main.py` — регистрация роутеров, middleware;
- `backend/app/services/orchestrator.py`, `backend/app/services/cache.py`, `backend/app/services/summary.py` (LLM-резюме);
- перенос легаси: `backend/app/services/profile.py`, `backend/tests/test_profile.py`;
- тесты: `backend/tests/api/`.

`backend/requirements.txt` — можно только **добавить** зависимость (например, `sse-starlette` или SDK LLM), упомяни в отчёте. Сборщики (`services/sources/`), пайплайн (`services/pipeline/`), `models.py`, `config.py`, `docs/CONTRACT.md` — не трогаешь. Если сборщика или функции пайплайна ещё нет, используй текущую легаси-реализацию и напиши об этом в отчёте — не пиши их за других агентов.

## Что сделать

**`GET /profile/{wikidata_id}?lang=` — SSE**
- До открытия стрима: валидация ID (422), Wikidata (404/503) — обычный JSON `ErrorResponse`.
- Сразу `source_status: pending` для всех источников из таблицы §3.
- Все источники параллельно (`asyncio`), каждый под `run_source`/своим таймаутом ≤ 8 с. Итоговый `source_status` с `count` и `took_ms` по завершении каждого.
- Кандидатов каждого источника сразу в `score()` → `Deduplicator.add()` → события `photo`. Цель — первое `photo` ≤ 5 с.
- Когда OSM вернул полигон — пересчитать уже отправленные фото и переотправить изменившиеся (тот же `id`).
- Общий дедлайн 30 с: по нему недоделанные источники получают `timeout`, стрим завершается `done`.
- `summary`: LLM (`LLM_API_KEY`) **только** по собранным текстам (Wikipedia, Wikidata, описания с официального сайта) — в промпт передаются тексты с номерами источников, модель обязана ставить `[n]`; ответ проверяется: каждая сноска есть в `citations`, иначе фоллбэк. Без ключа или при ошибке — выдержка из Wikipedia без переписывания (как сейчас). Нет текстов — пустое резюме.
- `done` — всегда последнее, `stats` по финальному состоянию.
- Отключение клиента — отменить задачи источников.

**Кэш** (`cache.py`) — готовый `ProfileResponse` по `(wikidata_id, lang)`, TTL; частичный профиль (были `timeout`/`error`) — короче TTL. Повтор из кэша проигрывает события и `done.cached = true`. Одновременные запросы одного профиля не должны запускать сборку дважды.

**`GET /campus/{wikidata_id}`** — по §4: форма кампуса и здания из OSM, `photo_pins` из кэша профиля (только фото с координатами, `building_id` по попаданию в здание), `city_center`/`distance_to_center_km` из Wikidata, `panoramas` — наличие покрытия Mapillary рядом с центром (и Kakao для Кореи при ключе), `checked_providers` — только реально проверенные. `transit` может быть `[]`.

## Проверка

- Тесты в `backend/tests/api/` на `httpx.AsyncClient`/`TestClient` с подменёнными сборщиками: порядок событий, `done` последнее, падение одного источника не ломает стрим, таймаут источника → `timeout`, общий дедлайн, повтор из кэша, 404/503 до стрима, форма `/campus`.
- `cd backend && .venv/bin/python -m pytest -q` — всё зелёное.
- Живой прогон: `.venv/bin/uvicorn app.main:app --port 8000`, затем `curl -N "http://localhost:8000/profile/Q39997?lang=ru"` — замерь время до первого `photo` и до `done`, приведи в отчёте. Сервер после проверки останови.
